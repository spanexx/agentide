What this feature is about

- Runtime capability pack that drives a real browser on behalf of an agent
  session: launch/close browser, open/list/close tabs, navigate, click, type,
  screenshot, wait. Engine: Playwright v1 (CDP/Rust rebuild = v2, out of scope).
- Session-scoped: one Chromium process + one BrowserContext per session;
  explicit `browser.launch`, `browser.tab.*` sub-namespace, session suspend
  keeps the browser alive, `session.closed` tears it down.
- Registers 12 capabilities with the capability-registry as owner `browser`
  (11 from T2 + `browser.query`, added by F8)
  (Runtime Manifest `runtime: { id: browser }`), dispatched in-process by the
  Gateway through `plugin:browser` owner.
- Delivers human observability in v1 as shape A "The window": headed mode +
  screenshot-on-demand, zero new surface (no event feed — that is
  dashboard-core BI[13] scope).

What this feature does NOT do

- Does not build a CDP (raw) engine or Rust rebuild (v2).
- Does not stream screenshots/events to a dashboard (dashboard-core BI[13]).
- Does not include Chrome DevTools extension integration (#14).
- Does not include a plugin-marketplace listing.
- Does not implement text=/role= selectors (CSS-only in v1).
- Does not add per-context proxy/interception config in v1 (defaults only).
- Does not add a hard concurrency cap or new launch-time session limits in v1.

Scope clarifications

- `capability.list` tabId filter is served by browser-runtime from its per-tab

  of the original Q5 answer, audit vs shipped code). Backward compatible
  exactly as Q5 promised: no-arg list unchanged, filter additive.
- Extends the T2 error-code table with three new codes: BROWSER_CRASHED
  (retryable: true) — see Q4 — BROWSER_NAVIGATION_DESTRUCTIVE
  (retryable: false) — see Phase 0.5 findings F7 — and BROWSER_SELECTOR_AMBIGUOUS

- Binary strategy: depends on `@playwright/browser-chromium` (exact-pin) — the

- Driver-first rule stands: plain-data `BrowserDriver` interface, zero Playwright

- Package lives at `packages/browser-runtime`, published as `@platform/browser-runtime`.

Questions and answers locked so far

1. How does the Chromium binary get installed?

Answer:
- Depend on `@playwright/browser-chromium` (exact-pin) as a direct dependency of
  `@platform/browser-runtime`. The browser binary is downloaded at install time
  by the package's postinstall and is guaranteed present whenever the pack is
  installed. No separate ops/plugin-install step.
- Why: plugin-manager installs the package; a dependency that self-provisions
  the binary means install == usable, zero extra steps for ops. The
  `playwright-core install chromium` route was rejected: it adds a manual step
  that is easy to forget and silently breaks launch at runtime.
- Decision record: CONTEXT.md (browser-runtime binary strategy, 2026-08-02).

2. Caps on simultaneous browser sessions in v1?

Answer:
- No hard cap in v1. One Chromium process hosts many BrowserContexts; each
  session = one context. Document ~10-20 concurrent sessions per host as
  practical guidance (memory-bound); operators control the envelope via host
  environment. A BROWSER_LIMIT_REACHED code is NOT added.
- Why: contexts in a shared process are comparatively cheap; a hard cap adds
  contract surface (new code, new failure modes) with no demonstrated need.
  Consistent with the T5 keep-alive-knob stance: no config/limit knobs until a
  real need exists. Revisit in v2 if memory pressure becomes measurable.
- Decision record: CONTEXT.md (browser-runtime concurrency limits, 2026-08-02).

3. Do v1 sessions need custom network/proxy configuration?

Answer:
- No. v1 uses Playwright's default network stack; each BrowserContext already
  isolates cookies/storage/state (locked in T1). Per-context proxy/interception
  options (`proxy: { server }`) are a v2 candidate.
- Why: no agent-loop use case surfaced in any ticket; proxy config adds option
  surface plus credential-handling questions for zero current value.
- Decision record: CONTEXT.md (browser-runtime network isolation, 2026-08-02).

4. What error surfaces when the browser process crashes mid-invocation?

Answer:
- New error code BROWSER_CRASHED, retryable: true, surfaced through the same
  GATEWAY_HANDLER_ERROR envelope as all BROWSER_* codes. The session is marked
  dead; the next browser.launch auto-relaunches (T1). BROWSER_CLOSED keeps
  meaning "browser intentionally closed (browser.close / session end)" and stays
  retryable: false.
- Why: T2's retryable policy is "timeout/race retryable, misuse not". A crash is
  definitionally a race, not misuse; reusing BROWSER_CLOSED would mislabel a
  recoverable condition as terminal, and its retryable:false flag would make
  agents abandon sessions that a simple relaunch fixes. Precedent: LAUNCH_FAILED
  is already retryable: true — a crash is the mid-flight sibling of a failed
  launch. One extra code keeps the retryable semantics honest.
- NOTE: This deviates from the agent's initial recommendation (reuse
  BROWSER_CLOSED); the recommendation was reversed during writing for the
  policy-consistency reason above. Flagged for user review.
- Decision record: CONTEXT.md (browser-runtime crash error code, 2026-08-02).

5. T4 locked `capability.list` tabId filter — extend shipped capability-registry
   now, or defer?

Answer (REVISED 2026-08-02, audit vs shipped code — see F9):
- The filter ships IN THIS PIPELINE, but it is served by browser-runtime from
  its own per-tab cap snapshot (captured at navigate, T4), NOT by modifying the
  shipped capability-registry. No-arg list passes through to the registry
  unchanged; `list({ tabId })` is answered by the runtime plugin.
- Why: the shipped registry keys records by name+version per owner
  (store.ts makeKey) and cards carry no owner/tabId (types.ts CapabilityCard) —
  it physically cannot distinguish tab 0's caps from tab 1's, and shipped
  sdk-browser has no tab awareness to pass as owner metadata. "Extend the
  registry" as originally locked would require a key-dimension change
  (name+version+tabId) + card schema change + sdk-browser tab awareness — a
  breaking change to a SHIPPED package for a need T4 already serves (navigate
  output carries per-tab caps; F7 same-url re-navigate = sanctioned re-read).
- Original answer recorded for traceability: "Extend now, same PR scope;
  registry change small and additive" — REVERSED by the grill-with-docs audit.
  Flagged for user review (delegated decision).
- Decision record: CONTEXT.md (capability.list tabId filter revision, 2026-08-02).

6. Pre-impl and post-impl simulation surface: HTML or CLI?

Answer:
- HTML simulation (interconnected-simulation skill, `simulate-pre.html` then a
  distinct `simulate.html`), same style as sdk-browser's.
- Why: browser state is inherently visual (tabs, URLs, screenshots); an HTML
  page with a terminal pane + state cards + live event log shows the agent loop
  against the browser far better than a CLI. Matches sibling-pack convention.
- Decision record: CONTEXT.md (browser-runtime sim surface, 2026-08-02).

Phase 0.5 findings — pre-impl simulation (2026-08-02, simulate-pre.html)

The pre-impl sim (HTML, interconnected-simulation skill) was built and verified
with Playwright (25/25 steps + full demo PASS, zero page errors). Building it
surfaced six findings — none change the locked contract, but the PRD-TRD and the
implementation MUST honor them:

- F1 tabId uniqueness (T2): launch seeds the tab counter at 1 (tab 0 is created
  by launch); ids increment per context and are NEVER reused — tab creation
  guards against handing out an existing id. Found as a real bug in the sim
  (launch forgot to seed → duplicate tabId 0), fixed + regression-tested. Real
  code note: after crash-relaunch the BrowserContext is new, so the counter
  resets — fresh context = fresh ids, consistent with "ids increment per
  context".
- F2 navigate targets the EXISTING tab (T2 confirmed): `browser.navigate { url,
  tabId? }` on an occupied tabId replaces that tab's page — never an error, and
  it does NOT open a new tab. Fresh tab requires `newTab: true` (sim flag:
  `navigate <url> new`). The sim mirrors this exactly.
- F3 browser.close { tabId } (T2 confirmed): with tabId = close just that tab,
  context intact; omitted = session teardown + process kill. Sim supports both
  paths.
- F4 async commands must be serialized: navigate/wait are async (500ms sim
  load); concurrent dispatch interleaves state. The sim serializes via a command
  chain. The real gateway already serializes per-invocation — the plugin must
  not introduce its own concurrency.
- F5 selector mapping is a sim-only detail: sim page elements are `#pg-*`
  ids while commands use real CSS selectors (`#input`, `#buy-btn`, ...); a
  SEL_MAP bridges them for visual flash feedback. The real implementation uses
  Playwright's real selectors — no mapping.
- F6 explicit `resume` before a post-suspend cap call is REDUNDANT (T5
  confirmed): gateway resume-first auto-resumes; the demo now shows
  suspend → type (auto-resume) with no explicit resume.
- F7 destructive-navigation guard (user review of the sim): a plain
  `navigate <url> <tabId>` on a tab whose page hosts registered
  capabilities silently destroys in-flight agent work (pagehide → caps
  unregister). New error `BROWSER_NAVIGATION_DESTRUCTIVE`
  (retryable: false — misuse, agent should have used `newTab`), thrown
  when the target tab has caps AND the url differs. Same-url re-navigate
  stays allowed (T4's sanctioned re-read), `newTab: true` always allowed
  (fresh tab), plain tabs (no caps) navigate freely. The runtime knows
  its own cap state and protects it. Extends the T2 error table (see
  Scope clarifications). Demo shows the guard: navigate www.google.com
  while tab 0 holds shop caps → error, demo continues.
- F8 instance disambiguation (user decision, product-list review): three
  `add.cart` buttons in one page = one registered capability type, but the
  agent must target a specific product. v1 adds THREE pieces (Option 3 of
  the user-review options):
  1. New read cap `browser.query { selector, tabId? }` → `{ matches,
     addresses }` — the runtime counts DOM matches and returns concrete
     CSS addresses (pid-anchored `[data-pid="202"] .add-cart`, else
     nth-of-type) the agent can reuse verbatim. 0 matches is a RESULT
     (`matches: 0`), never an error — query exists to teach the agent.
  2. `instance` param on click/type (`{ selector, instance?: number, ... }`,
     1-based) — resolves the nth match internally; no selector gymnastics.
  3. `BROWSER_SELECTOR_AMBIGUOUS` (retryable: false, misuse) — click/type on
     a selector with >1 matches and no instance refuses instead of clicking
     the first element blindly (same F7 philosophy: runtime refuses silent
     wrong actions; the error carries the matches count).
  Id-based selectors work on arbitrary pages (`[data-pid]`-style attributes
  sites already emit); query is what makes the agent KNOW the ids exist —
  the portable equivalent of sdk-browser's `data-product-id` handshake
  (GRILL-sdk-browser) without needing a cooperative page. Extends the T2
  error table (see Scope clarifications). Sim: product list on shop page
  + query/instance/guard demo + tests.
- F9 capability.list tabId filter — served by browser-runtime, registry
  UNTOUCHED (revision of Q5, grill-with-docs audit vs shipped code): the
  shipped capability-registry keys records by name+version per owner
  (store.ts makeKey), CapabilityCard has no owner/tabId (types.ts), and
  register() replaces the owner's map (index.ts) — it cannot hold per-tab
  cards; shipped sdk-browser has no tab awareness to pass as owner metadata.
  Per the user's mandate ("criticize answers against docs and
  implementation"), Q5's "extend the shipped registry" answer was reversed:
  browser-runtime keeps a per-tab cap snapshot (captured at navigate, T4)
  and serves `capability.list({ tabId })` from it; no-arg list passes
  through unchanged — backward compatible exactly as Q5 promised, without
  cross-package surgery. Re-read path stays: navigate output + F7 same-url
  re-navigate. Flagged for user review (delegated decision).
