## problem

the operator's day-2 workflow is: mint a JWT, paste it into the consumer's
`.env`, watch it expire (1h default), paste a new one. repeat forever. the
SDK has no way to refresh. the consumer has no client identity. the
operator is the bottleneck.

## questions

Q1 — identity model.
  a) client_credentials (OAuth2 style): every consuming app has a client
     id + client secret. SDK uses them to mint short-lived JWTs at
     POST /oauth/token. refresh is automatic.
  b) refresh tokens (long-lived opaque token that mints short-lived JWTs).
  c) mutual TLS (cert-based, no shared secret).
  d) static JWT only (what we have today).
  -> pick (a). standard, simple, works for both apps and agents. (c) is
     overkill for v1. (b) is a marginal improvement that adds moving
     parts without solving the operator-paste problem.

Q2 — operator's role.
  a) operator mints `client_id + client_secret` ONCE per app lifetime.
  b) operator approves registration codes issued by the app on first boot.
  c) operator is always online and handles every token mint.
  -> (a) for the common case + (b) for the offline-friendly case. (c) is
     what we have today; it's the bottleneck.

Q3 — where does the operator's one-time output go?
  a) prints to stdout (today's pattern).
  b) writes to a file with 0600 perms under <data-dir>/clients/.secret-<id>.txt
     and prints only the path.
  c) both via a flag.
  -> (b) default, (a) via `--print`. the secret never hits scrollback.
     the operator shells the file contents into the app's env and
     deletes the file from their downloads directory.

Q4 — transports.
  a) only websockets (current SDK).
  b) websockets + a new HTTP endpoint for the OAuth flow.
  -> (b). the OAuth flow is request/response; fits HTTP cleanly. the
     existing MCP adapter already serves HTTP on :7100. add
     POST /oauth/token to that.

Q5 — TLS.
  a) assume TLS termination at the load balancer.
  b) require TLS at the gateway (refuse plaintext).
  c) both — gateway refuses plaintext unless --no-tls is set for dev.
  -> (c). production deployments must have TLS; localhost dev can opt out.
     a single line in the gateway config. the refusal is loud (426
     Upgrade Required) so operators can't accidentally enable
     anonymous plaintext auth.

Q6 — registration-code flow.
  a) none. operator hands the secret to the app directly.
  b) operator runs `agentide client grant --name X` and gets a one-time
     code. the app redeems the code at first boot to get its own
     client_id + client_secret.
  -> (b). lets the operator be offline. supports "I'll spin up a new app
     tomorrow" workflows where the operator isn't online.

Q7 — OIDC for humans.
  a) defer; build client_credentials only.
  b) include now: a separate authorization-code grant for user-delegated
     tokens. production swap-in for SSO.
  -> (b). the user explicitly asked for production-ready. OIDC is the
     standard production answer for human-issued tokens. deferring
     leaves a half-built system.

Q8 — backward compatibility.
  a) break the existing PLATFORM_TOKEN static-JWT path.
  b) keep it for clients that opt into it. new install path uses
     client_credentials.
  -> (b). no regressions. the SDK reads `clientId + clientSecret` if
     both are set, otherwise falls back to `token`. secret upgrades
     work file-by-file without coordinated upgrades.

## decisions

Q1: (a) client_credentials
Q2: (a) operator mints client credentials + (b) optional registration code
Q3: (b) default writes to file + path printed; (a) via --print flag
Q4: (b) HTTP POST /oauth/token on the existing MCP adapter
Q5: (c) --require-tls default true; --no-tls for dev
Q6: (b) registration-code flow with 5-min TTL
Q7: (b) OIDC auth-code grant included
Q8: (b) legacy PLATFORM_TOKEN path preserved
