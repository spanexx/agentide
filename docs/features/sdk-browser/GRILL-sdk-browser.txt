Source: Wayfinder map #8 (sdk-browser), ticket #9 (T2 Manifest and handler transport)

What this feature is about

- Browser-side SDK that lets a web app expose business capabilities to the Gateway,
  mirroring @platform/sdk-node's role for Node apps.
- The SDK reads `data-sdk-cap` attributes from the live DOM via MutationObserver and
  registers each cap with the Gateway. Inbound invocations dispatch as CustomEvents on
  the annotated element; dev-supplied `addEventListener` handlers respond.
- Sits inside the page; runtime execution of the actual handler lives in the page's own
  listener code. Browser Runtime (separate map, #12) is the consumer-facing counterpart
  that drives the browser, not the registration surface.

What this feature does NOT do

- Does not own a separate capability manifest file (manifest = DOM).
- Does not maintain a handler registry in the SDK (handlers = page listeners).
- Does not drive browser automation (that's Browser Runtime).
- Does not include a marketplace listing, multi-language variants, Chrome DevTools
  extension, or Service-Worker-based persistence (out of scope for v1).

Scope clarifications

- v1 assumes the same wire protocol as sdk-node (8 lifecycle events, JWT handshake,
  `sdk.invoke` / `sdk.invoke.result` / `sdk.invoke.error`), reused from
  `@platform/backend-runtime` (BI[8b]).
- All gating decisions from T1 (CONTEXT.md:162) remain binding.

Questions and answers locked so far

1. Given T1's DOM-annotation model, do we still need a manifest file at install time?
   Or does the SDK `init` only take `{ gateway, appId, token }` and rely on
   `MutationObserver` for the cap inventory?

Answer:
- No manifest file. `createSdk({ gateway, appId, token, observeRoot?, defaultTier?,
  defaultVersion? })` — cap inventory comes entirely from `MutationObserver` walking
  `data-sdk-cap` attributes.
- Closes ticket sub-questions 1-3 (manifest source, handler source, validation) as
  moot: no manifest to source, no handler map to load, no manifest schema to validate.

Why:
- A manifest would be a parallel source of truth devs must keep in sync with the DOM —
  defeating T1's annotation model.
- Node SDK needs a manifest because Node has no DOM to introspect; browser SDK has
  the DOM as its manifest.
- Dev's handlers live as `addEventListener('sdk:cap:<name>', ...)` on the annotated
  elements — outside the SDK, so no handler map to load either.
- Lazy mount is handled by the observer (registers when the element enters the DOM);
  programmatic invocation from page code uses the SDK's own `invoke()` (same shape
  as sdk-node).
- Rules out for v1: caps with no DOM element (use sdk-node for those);
  programmatic cap registration without a DOM element (defer to v2 unless a real
  use case shows up).

Source: T1 lock at `agentide/docs/CONTEXT.md:162`; sdk-node's `manifest.ts` shape
(`packages/sdk-node/src/manifest.ts`) is the parallel we're choosing *not* to mirror.

(No remaining open questions in this section yet — more to follow for cap-extraction
edge cases: observe scope, attribute set, dedup, removal-on-unmount.)

2. Which `data-sdk-*` attributes does the SDK actually read from annotated elements?

Answer:
- The SDK reads only `data-sdk-cap` (the cap name) from each annotated element.
- Tier and version come from config-level defaults applied SDK-wide:
  `createSdk({ ..., defaultTier: 'act', defaultVersion: '1.0.0' })`.
- No per-element overrides in v1.

Why:
- T1's lock authorized the `data-sdk-*` family but did not enumerate its members;
  T2 fills the family in with restraint.
- Per-element tier/version overrides fragment the cap model — same cap name
  registered with different tiers on different elements is a debugging nightmare.
- Form-fill input mapping is per-element in shape, but is a DX concern that lives in
  T4 (Frontend developer experience), not a registration concern.
- Config-level defaults cover the 95% case; the 5% can wait for v2.

Rules out for v1:
- `data-sdk-tier` per-element override
- `data-sdk-version` per-element override
- `data-sdk-input` static default input on the element
- `data-sdk-target` selector pointing to a different dispatch target
  (v1 always dispatches on the annotated element itself)

Source: T1 lock at `agentide/docs/CONTEXT.md:162` ("Metadata location = inline
`data-sdk-*` attributes" — family, not required-many); T4 owns DX surface
decisions; CONTEXT.md default tier `act` / default version `1.0.0`.

3. What does the SDK observe, and what about pre-mounted elements, shadow DOM, and iframes?

Answer:
- Initial scan of the observe root on `createSdk()` — picks up all annotated elements
  already in the DOM.
- `MutationObserver` watches the observe root for added/removed nodes + attribute
  changes: `subtree: true, childList: true, attributes: true,
  attributeFilter: ['data-sdk-cap']`.
- Default observe root = `document.body`; overridable via
  `createSdk({ observeRoot: someElement })`.
- v1 does NOT pierce shadow DOM — `MutationObserver` doesn't observe into shadow
  roots natively. Devs attach their own observer per root and forward to the SDK
  via `sdk.observe(rootElement)`.
- v1 does NOT pierce iframes — cross-origin is impossible; same-origin is out of
  scope.

Why:
- Most annotated elements live in the static HTML, not in lazy-loaded JS — initial
  scan is required, not optional.
- Shadow DOM piercing is non-trivial and `MutationObserver` doesn't do it natively;
  explicit `sdk.observe()` per root keeps the design honest.
- iframe piercing is a security/policy minefield; out of scope for v1.

Rules out for v1:
- Automatic shadow DOM piercing
- iframe content observation (cross-origin and same-origin)
- Configurable `attributeFilter` beyond `data-sdk-cap` (T2 doesn't read other
  `data-sdk-*` per Q2)

Source: WHATWG DOM Living Standard (`MutationObserver` semantics); Q2 lock
(only `data-sdk-cap` is read); sdk-node has no analog (no DOM); T1 lock at
`agentide/docs/CONTEXT.md:162`.

4. If the same `data-sdk-cap="invoice.create"` appears on N elements, do we
   register once or N times?

Answer:
- Deduplicate. Register one cap per name.
- SDK internally tracks the count of annotated elements per cap name.
- Register when count goes 0 → 1 (first annotated element enters the DOM).
- Unregister when count goes 1 → 0 (last annotated element leaves the DOM).

Why:
- The Gateway doesn't care how many UI elements back a cap — it cares that the
  cap exists.
- "Which element gets the dispatched event when several are visible" is a
  runtime question, not a registration question — that's T4 (Frontend developer
  experience) territory.
- Counts-based registration is symmetric (add ↔ remove) and idempotent.
- Matches the principle: *registration = presence of affordance*, not
  *registration = UI element*.

Rules out for v1:
- Registering N copies of the same cap with disambiguating suffixes.
- A `data-sdk-primary` hint to mark a canonical element per cap.
- Per-element cap identity (e.g., `invoice.create#row-42`).

Source: standard `MutationObserver` add/remove symmetry; T1 lock at
`agentide/docs/CONTEXT.md:162`; T4 owns DX surface (which element receives the
dispatched event).

5. When `add_to_cart` is invoked and the page has 50 buttons annotated with
   `data-sdk-cap="add_to_cart"`, which button(s) receive the dispatched event?

Answer:
- Fan-out by default. The SDK dispatches a CustomEvent on every annotated
  element with that cap name.
- Each listener receives the same `detail: { input, ctx }` and decides whether
  to act (filter by input match against DOM context like `data-product-id`).

Dev pattern (single delegated listener on `document`):
  document.addEventListener('sdk:cap:add_to_cart', e => {
    const btn = e.target.closest('[data-sdk-cap="add_to_cart"]');
    if (!btn) return;
    if (Number(btn.dataset.productId) === e.detail.input.productId) {
      addToCart(btn);
    }
  });

Why:
- The SDK has no way to know which button is "right" for a given input — only
  the dev knows (via DOM context).
- Fan-out makes the SDK dumb and the dev explicit — easier to debug than hidden
  routing.
- The CustomEvent is a signal, not an action — listeners are cheap; the filter
  is the dev's job.
- Matches T1's lock ("CustomEvent DOM dispatch") without forcing the SDK to
  make per-invocation element-selection decisions.

Rules out for v1:
- SDK picking one element (which one? first? last? visible? — all arbitrary).
- Dev-supplied dispatch handler at registration time (this is what sdk-node does;
  we're choosing not to mirror it).
- Per-element dispatch targeting via attributes (ruled out in Q2).
- A "primary element" marker per cap (ruled out in Q4).

Source: standard `CustomEvent` semantics (WHATWG DOM); T1 lock at
`agentide/docs/CONTEXT.md:162`; Q2 lock (no per-element target attribute); Q4
lock (one cap per name, fan-out resolves the multi-element case).

### T5 / Q1 — Auth transport (locked 2026-07-30)
Decision: Browser SDK sends `{type: "sdk.auth", token}` as the first message body
after `onopen`, identical to sdk-node's secondary auth path. No `Authorization`
header (impossible in WHATWG WebSocket, server ignores it anyway). Zero new
server code. Rules out: `?token=...` query (logs leak JWTs), `Sec-WebSocket-Protocol`
(subprotocol is for protocol multiplexing, surfaces in dev tools + proxy traces).

### T5 / Q2 — Origin binding (locked 2026-07-30, PERMANENT — not a v1 patch)
Decision: every browser SDK token MUST carry a signed
`expectedOrigins: string | string[]` JWT claim. `backend-runtime` reads the
claim after `verifyToken` succeeds; if inbound `Origin` doesn't match (with
`*.subdomain` wildcard support), close the socket with code 1008. Mandatory,
no opt-out. Dev mode handled by issuing tokens for `http://localhost:port`.
`auth.token.issue` CLI gains `--kind browser` + `--origin` / `--origins` flags.
Solves stolen-token-replay-on-rogue-origin (`acme.com`'s token used on `evil.com`).

### T5 / Q3 — JWT forwarding to handlers (locked 2026-07-30)
Decision: forward caller's JWT **verbatim** via `e.detail.ctx.token`, mirroring
sdk-node's existing decision. Verified at [invoke.ts:101](file:///home/spanexx/Shared/Learn/Agent-Bridge-SDK/agentide/packages/sdk-node/src/invoke.ts#L101) and
[invoke.ts:147](file:///home/spanexx/Shared/Learn/Agent-Bridge-SDK/agentide/packages/sdk-node/src/invoke.ts#L147). Rules out: claims-only
forwarding (breaks handler-side validation; future token-rotation depends on
raw tokens); both claims + raw token (duplicate surface).

### T5 / Q4 — Browser-native WebSocket only (locked 2026-07-30)
Decision: `globalThis.WebSocket` only. No polyfill, no fallback. SDK throws on
construction if missing. `ws` Node library is not bundled (Node-only deps).
Server-side `WebSocketLike` at [types.ts:89-92](file:///home/spanexx/Shared/Learn/Agent-Bridge-SDK/agentide/packages/backend-runtime/src/types.ts#L89-L92) is just
`send`/`close`, both of which native browser `WebSocket` already has. Drift
D-13 (`ws-shim.cjs`) is sim-only.

## T3 — Browser-aware reconnect and lifecycle (started 2026-07-30)

Source: Wayfinder map #8 (sdk-browser), ticket #10 (T3). Status: grilling in progress.

### T3 / Q1 — Visibility (locked 2026-07-30)

Question: when the tab goes hidden (background tab throttling), what does the
SDK do about reconnect attempts?

Answer:
- **Pause reconnect while hidden; resume immediately on `visibilitychange` to
  "visible"**.
- Subscribe to `document.addEventListener('visibilitychange', ...)`.
- On `'hidden'`: clear any pending reconnect timer, mark state as "waiting for visible".
- On `'visible'`: if state was "waiting for visible" AND we want to be connected,
  fire the reconnect immediately.
- The reconnect schedule (1s, 2s, 4s, 8s, 16s, 30s cap, ±20% jitter) is unchanged
  from sdk-node's pattern; visibility gates *when* it fires, not the curve.

Why:
- The user can't see what's happening while the tab is hidden. Reconnect
  attempts are wasted work.
- Throttled timers in backgrounded tabs can stack up and all fire on
  visible-transition — a small thundering herd.
- Closing the socket on hide is too aggressive: every tab switch drops the
  connection, every switch reopens it. The cap set flickers on every switch.
  Multi-tab same-origin pages would lose caps when one is hidden.

Rules out:
- (B) always-reconnect, ignore visibility.
- (C) close-on-hide, reopen on visible.
- A "smart" mode that uses a different backoff curve when hidden.

Source:
- WHATWG Page Visibility API (`document.visibilityState`, `visibilitychange` event).
- WHATWG HTML Living Standard background-tab throttling rules.
- sdk-node backoff schedule (BI[8]).
- T3 ticket sub-Q 1.
- Mirror in `agentide/docs/CONTEXT.md` Decisions Log: 2026-07-30 sdk-browser T3 Q1.

### T3 / Q2 — Online/Offline (locked 2026-07-30)

Question: what does the SDK do when the browser fires `online` or `offline`?

Answer:
- `window.addEventListener('online', ...)` and `window.addEventListener('offline', ...)`.
- On `offline`:
  - Mark state as `'offline'`.
  - Clear any pending reconnect timer (saves a wasted attempt).
- On `online`:
  - Clear the `'offline'` state.
  - **Reset the backoff** — next reconnect uses the initial delay, not the
    next-in-curve delay. The previous backoff is stale; the failure was "old."
  - If we want to be connected AND not currently connected, fire the reconnect
    immediately.

Why:
- The user came back online. The previous backoff schedule is stale (it's a
  countdown from when the socket died, not from "now"). 30s of staring at a tab
  after a tunnel transit is bad UX.
- `offline` is preemptive — the socket is going to fail anyway; marking it dead
  prevents wasted reconnect attempts that land during the offline window.
- The `online` event tells us "you should retry now." We retry now.
- Resetting backoff is the key new behavior — it's what makes "coming back
  online" feel responsive.

Rules out:
- (B) ignoring the events — let natural close + backoff handle it. Up to 30s
  of dead air after coming back online.
- (C) using events as hints without skipping backoff — backoff's purpose is to
  avoid hammering a failing server; on `online` the server isn't failing, the
  path was lost.
- Polling `navigator.onLine` — events already cover it; polling is wasteful.

Source:
- WHATWG HTML Living Standard — `window.online` / `window.offline` events,
  `navigator.onLine` getter.
- T3 ticket sub-Q 2 (stated default matches).
- Interacts cleanly with T3 Q1: if hidden AND offline, no fire; if visible AND
  online, fire immediately.
- Mirror in `agentide/docs/CONTEXT.md` Decisions Log: 2026-07-30 sdk-browser T3 Q2.

### T3 / Q3 — Page unload (locked 2026-07-30)

Question: when the LLM agent's browser session moves on or ends (`pagehide`
fires on the web owner's page), what does the SDK do?

Context reminder: the SDK runs in the web owner's page; the LLM agent drives
the browser session. "User" = the LLM agent's browser session, not a human.

Answer:
- Listen for `pagehide`.
- If `event.persisted === true` (page is going into bfcache — LLM agent's
  "back" button or browser restoring a frozen page): do nothing. The
  WebSocket stays alive for fast restore.
- Else (real unload, LLM agent truly leaves or session ends):
  - Try to send `{ type: "sdk.disconnect", reason: "pagehide" }` via
    `WebSocket.send(...)`.
  - Call `WebSocket.close(1000, "pagehide")` (1000 = normal closure).
  - Don't await. The browser may close the socket before the message is
    flushed. Best-effort.

Why:
- The gateway benefits from `sdk.disconnect`: it can unregister the cap
  immediately instead of waiting for TCP timeout (which can be minutes).
  During the timeout window, agents calling the cap get `HANDLER_TIMEOUT`.
- Bfcache awareness is critical. LLM agents navigate "back" and "forward"
  frequently; if we close on every pagehide, the connection dies on every
  back-nav and has to reconnect.
- We don't await the send because the browser won't wait. Best-effort is
  the only honest framing.

Rules out:
- (B) close-without-message — gateway has to wait for TCP timeout.
- (C) `navigator.sendBeacon` — HTTP POST, wrong transport.
- Using `unload` instead of `pagehide` — deprecated, bfcache-unfriendly.
- Awaiting the send before closing — browser won't wait, don't pretend.
- Service Worker to persist connection across navigations — out of scope for v1.

Source:
- WHATWG HTML Living Standard — `pagehide` event, `PageTransitionEvent.persisted`
  for bfcache.
- WHATWG WebSocket — `close(code, reason)`, code 1000 normal closure.
- T3 ticket sub-Q 3 (stated default matches).
- Mirror in `agentide/docs/CONTEXT.md` Decisions Log: 2026-07-30 sdk-browser T3 Q3.

### T3 / Q4 — Heartbeat (locked 2026-07-30)

Question: which side initiates the liveness check?

Answer:
- **Server-initiated ping only; browser SDK unchanged.**
- `backend-runtime` sends a protocol-level ping every 30s per socket.
- Browser auto-pongs at the protocol layer (the browser's `WebSocket` API
  handles ping/pong transparently — page JS never sees them).
- If `backend-runtime` doesn't see a pong within 10s, it closes the socket
  with code 1011 ("heartbeat timeout").
- The browser fires a `close` event; the SDK's existing close handler
  triggers the reconnect.
- **Zero browser SDK code change.** Same mechanism works for sdk-node
  (Node `ws` library also handles ping/pong transparently).

Why:
- The browser-side `WebSocket` API is special: it cannot observe ping/pong
  at the JS layer, so "client-initiated" for the browser would have to mean
  app-level wire messages.
- `setTimeout`-based heartbeats in backgrounded tabs are exactly the kind of
  thing that gets throttled, making them unreliable. The protocol-level ping
  is the right tool.
- One implementation in `backend-runtime`, two clients (sdk-node + sdk-browser)
  benefit.

Rules out:
- (B) client-initiated app-level heartbeat — duplicates what the protocol
  already does, more wire messages, less reliable in backgrounded tabs.
- (C) both — over-engineering.
- "No heartbeat" — silent dead-but-TCP-up connections are a real failure
  mode; the gateway would never know.

Source:
- WHATWG WebSocket / RFC 6455 — protocol-level ping/pong, browser auto-pong.
- Node `ws` library — `socket.ping()` server-side, transparent pong.
- T3 ticket sub-Q 4.
- Mirror in `agentide/docs/CONTEXT.md` Decisions Log: 2026-07-30 sdk-browser T3 Q4.

## T3 — Resolution summary (2026-07-30)

All four sub-questions of T3 are locked. The lifecycle shape is:

1. **Visibility (Q1):** Pause reconnect while tab is hidden; resume on
   `visibilitychange` to "visible". Reconnect schedule (sdk-node's) gated
   on visibility.
2. **Online/Offline (Q2):** Treat socket as dead on `offline`; reset
   backoff + fire reconnect immediately on `online`.
3. **Page unload (Q3):** Best-effort `sdk.disconnect` on `pagehide`, then
   `WebSocket.close(1000, "pagehide")`. Bfcache-aware: skip on
   `event.persisted`.
4. **Heartbeat (Q4):** Server-initiated protocol-level ping every 30s
   from `backend-runtime`. Browser auto-pongs. 10s pong timeout → close
   with code 1011. Zero browser SDK code change.

T3 ticket is closable. Next: T4 (Frontend developer experience — prototype
ticket, works differently from grilling).

Why:
- The root config is one file with no environment set; a per-package
  config would force converting it to vitest `projects`, touching the
  test setup of all existing packages.
- jsdom covers every DOM API the SDK uses: `MutationObserver`,
  `CustomEvent`, `closest()`, `visibilitychange`/`pagehide` event
  plumbing.
- `@vitest/browser` would need a real browser binary in CI — slower,
  flakier, and overkill for v1.
- The WebSocket stub is a ~30-line fake; it is a test fixture, not a
  polyfill (T5 Q4 lock stands: no production fallback).
- Rules out: (B) per-package config + `projects` conversion; (C)
  `@vitest/browser` for v1.

Source: T6 ticket sub-Q 4; `agentide/vitest.config.ts` (root, no
environment); jsdom lacks WebSocket (documented limitation); T5 Q4 lock
(no polyfill).

### T6 / Q5 — Bundle size budget (locked 2026-08-01)

Answer:
- **No hard cap for v1.** Record a soft guideline instead: exactly one
  runtime dependency (`@platform/event-bus`, ~440 lines of pure TS) and
  ESM-only output, so consumers' bundlers tree-shake unused code.
- If size ever becomes a problem, the check is easy to add later —
  bundler + CI size check — but that is new tooling for a package that
  does not have a size problem yet.

Why:
- The repo ships plain `tsc` dist today; a hard cap would force adding a
  bundler (esbuild) + a CI gate — new tooling, new maintenance.
- The discipline that matters is dependency count, already locked at one
  runtime dep by Q3.
- Rules out: (B) hard cap with CI enforcement now; (C) manual soft-budget
  tracking (the README/ship-time note adds process without a number to
  enforce).

Source: T6 ticket sub-Q 5; Q3 lock (single runtime dep); sdk-node ships
plain `tsc` dist (no bundler in the monorepo).

### T4 / D1 — Canonical install path (locked 2026-08-01)

Question: which shape becomes the canonical v1 install — Shape A (bundler
import), Shape B (`<script>` tag), or both?

Answer:
- **Shape A only for v1** — `npm install @platform/sdk-browser` +
  `import { createSdk } from '@platform/sdk-browser'`. Bundler
  (Vite/webpack/Rollup) resolves the bare specifier.
- The `<script>` tag / IIFE path is deferred to a v1.1 follow-up ticket
  with a named trigger: a real no-bundler consumer shows up.
- **This resolves T6 Q1 (was HELD):** build output = ESM-only. No IIFE
  build, no `browser` field in v1.

Why:
- The prototype proved both shapes run identical dev code
  (`demo-doc.js` + `sdk-core.js` shared) — the decision is install-only,
  and A matches the modern default, mirrors sdk-node's install model,
  and needs exactly one build (T6 Q2 already locked ESM-only).
- B would add a second build + CDN hosting + a global namespace
  (`PlatformSdk`) for an unproven path; C doubles packaging from day one.
- Evolution model: v1 covers the 95% case; each deferred surface has a
  named trigger (see GRILL T4 D1 discussion — v2 items table).
- Rules out: (B) script-tag canonical; (C) both from day one.

Source: T4 ticket sub-questions; prototype README comparison
(`prototypes/sdk-browser-dev-experience/README.md`); T6 Q1 HELD entry
(above); sdk-node install model (npm + config + connect).

### T4 / D2 — Framework helpers (locked 2026-08-01)

Question: do framework-native helpers (`useSdk()` for React, composable
for Vue, store for Svelte) ship in v1?

Answer:
- **No. Punt all framework helpers to v2.** v1 is framework-agnostic:
  `createSdk()` + the 8 lifecycle events + `onStateChange()`.
- Trigger to revisit: the first framework team that adopts sdk-browser
  and asks for the shortcut — then add that one framework's helper.

Why:
- The plain `createSdk()` setup is ~15 lines and works in any framework;
  helpers are thin wrappers saving ~10 lines.
- Each helper is a new maintained surface with framework-specific traps
  (hooks lifecycle, SSR, stale state) — three implementations, three
  test matrices, zero named customers.
- Same deferral pattern as every other v2 item: add when someone needs
  it, not before.
- Rules out: (B) React-only `useSdk()` in v1; (C) all three in v1.

Source: T4 ticket "What I don't know" (framework helpers); v2-deferral
pattern across T1/T2/T3 grills.

### T4 / D3 — Connection-state surface (locked 2026-08-02)

Question: how does v1 surface connection state to UI code ("connecting",
"reconnecting", "disconnected") without forcing the consumer to subscribe
to all 8 lifecycle events?

Answer:
- **`sdk.onStateChange(cb)`** — a dedicated callback, invoked only on
  actual transitions, with exactly four states:
  `connecting | connected | reconnecting | disconnected` (no duplicate
  callbacks for the same state; synchronous `sdk.state().connectionState`
  getter returns the current value for render-on-load).
- The 8 lifecycle events stay as-is for tooling/logging; `onStateChange`
  is the UI-facing surface, not an event-bus subscription.
- v1 API adds exactly one function + one field on the existing `state()`
  getter. No framework helpers (D2), no new event.

Why:
- The T4 prototype already demonstrates the pattern
  (`sdk-core.js` `setConnState` → `stateCbs.forEach(cb => cb(next))`;
  both shape pages drive their lifecycle badge from it; Playwright 4/4).
  Reacting to the artifact is the whole point of a prototype ticket.
- sdk-node parity: sdk-node exposes `state().phase`
  (`init|connected|registered|disconnected`) but no callback and no
  `reconnecting` state — its consumers are servers; sdk-browser's
  consumers are UIs, where "reconnecting" (hidden tab, offline, T3
  gates) is a state the user must SEE. The callback closes the
  "subscribe to all 8 events and derive phase yourself" gap the ticket
  named.
- Rules out: (B) fold into the 8 events only (forces every UI consumer
  to re-derive state across events — exactly the friction D3 asked to
  avoid; one missed event = wrong badge); (C) an additional unified
  `sdk.state` event on the event-bus (the event-bus is an internal
  surface — sdk-node's own consumers subscribe via `sdk.on`, not the
  bus; zero named consumers for a second path).

Source: T4 ticket "What I don't know" (connection-state); prototype
`sdk-core.js` (lines 19-20, 33-36, 53-68, 202-217); sdk-node
`src/types.ts` `Phase` (no `reconnecting`); T3 grills (visibility /
online-offline gates produce the `reconnecting` state).
