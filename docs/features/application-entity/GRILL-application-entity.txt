Application Entity - Grill Notes

Status: Locked (8 questions locked)
Date: 2026-07-31
Source: docs/.reports/Agentide Production Audit_ Security, Performance &
Design Patterns.md (Section 1.1 — Multi-Tenant Isolation Bypass via Backend
SDK Connection Keying), PR #17 (docs/production-risks-log.md), sibling
packs gateway-core/sdk-node/backend-runtime, PHILOSOPHY.md,
docs/CONTEXT.md

What this feature is about

- Introduce a first-class Application entity as the immutable, per-tenant
  SDK/client identity. Each Application has a platform-generated UUID
  (primary identifier) and a human-readable name (display label).
- The UUID is the primary key everywhere: connection registry, capability
  owner, rate-limit bucket key, audit log, session creation. The name is
  denormalized in tokens and logs for display only.
- The shape is `Application { id: "app_<ulid>", tenantId, name, createdAt }`.
  The id never changes after creation. The name is editable and used for
  humans, logs, dashboards, CLI.
- This is the architectural fix for the multi-tenant isolation bypass
  documented in the production audit (Section 1.1). The registry no longer
  keys by `callerId` (which collides across tenants); it keys by a UUID
  that is unique platform-wide.
- Renames do not break references. The connection from a token issued
  yesterday still resolves to the same socket after a rename today,
  because the lookup is by id, not name.
- Cloning, importing, moving applications become trivial (UUID is the
  reference). Not in v1 surface, but the data model supports it.

What this feature does NOT do

- It does NOT add a marketplace, a developer portal, or an app catalog UI.
  v1 ships a CLI and a JSON file store. Anything fancier is a separate
  pack.
- It does NOT change the SDK wire protocol beyond the auth acknowledgement.
  `sdk.auth` still carries `{type, token}`. The server adds
  `sdk.auth.ack { applicationId, applicationName }` so SDKs can log
  and persist the id locally.
- It does NOT solve token revocation (separate pack — revocation
  denylist). A deleted app's old tokens remain valid until natural expiry.
- It does NOT add hierarchical/nested applications. One tenant, many
  applications, flat list.
- It does NOT add per-application roles or scoped permissions. The scope
  semantics stay on the token claim (`CallerIdentity.scope`) — the
  application is just the identity the scope is bound to.

Questions and answers locked so far

1. "Or a generated UUID such as app_9c4f82... I think that's the cleaner
architecture. Instead of this: Tenant ID + Application ID ('portfolio-service')
I'd define: Application UUID (immutable, platform-generated, primary identifier)
+ Application Name (human-readable, editable) ... The runtime, registry,
sessions, permissions, and SDK connections should all use the UUID. The name
is only for humans, logs, dashboards, and CLI output."

Answer:
- Each Application has a UUID id (the primary key) and a string name
  (display). The id is generated by the platform at Application creation,
  immutable forever. The name is editable, per-tenant unique, used only
  for display.
- All runtime lookups (registry, capability owner, rate-limit bucket,
  session attach, audit log) key by the UUID id. The name appears only
  in the token claim (denormalized), in logs, in CLI output, in
  dashboards.
- Suggested id format: ULID-like (`app_01K2X8T6ZP4JY3N5W7R9A1B2C`) —
  sortable by creation time, URL-safe, no central coordinator needed
  for generation. Implementation detail deferred to IMPL; the contract
  is "opaque, unique, immutable."

Why:
- "No collisions, ever" — UUIDs are unique across tenants by construction.
  Two tenants can name their apps "portfolio-service" with zero risk.
- "Applications can be renamed without breaking references" — the UUID
  is the reference; the name is nullable for rename grace (or simply
  cached as stale until token refresh).
- "SDK lookups become a single map lookup" — the registry's Map keyed on
  the UUID; no parsing, no prefix matching, no tenant scoping in the key.
- "The audit issue disappears entirely" — the bug at audit Section 1.1
  (collision when callerId is reused across tenants) cannot occur.
- "Future features like cloning, importing, or moving applications become
  much easier" — UUID is the reference; clone = new Application with
  the same name + new id; rename = name field change, id and references
  stable.
- Sources: user-proposed architecture in this session; audit Section 1.1;
  PHILOSOPHY.md "Nothing Is Special" — the application is now a real
  entity, not a string overloaded to be both id and name.

2. "Should `applicationId` be carried in the JWT or resolved at first connect?"

Answer:
- In the JWT. The token carries `applicationId` and `applicationName` in
  the `sub` claim. The registry's connection key is the applicationId.
- The Application store is consulted at token issuance (to bind the id)
  and for ACL checks (suspended, deleted). It is NOT consulted per
  invocation.

Why:
- Every request is self-contained — no DB lookup needed to resolve the
  identity. Decoupling from the registry means the token's identity is
  stable across reconnects.
- Multi-replica deploys (future pack) work without a shared cache — every
  replica can verify the token independently.
- Token expiry is the natural revocation window. For v1, accept that a
  deleted application's old tokens remain valid until natural expiry.
  Revocation is a separate pack.
- Rules out: tokenless connection (server must hold the applicationId
  in a side cache), per-request Application store lookup (latency).

3. "Should `applicationName` be in the token claim (denormalized) or
re-fetched per request?"

Answer:
- Denormalized in the token claim. The token carries the name frozen at
  issuance time. The Application store is the source of truth for ACL but
  is NOT consulted for the name on every request.

Why:
- Zero DB lookup per request for display purposes.
- Stale names are acceptable for audit logs and dashboards — they show
  the name the caller was known by when the token was issued, which is
  arguably the most accurate attribution for audit.
- After a rename, the operator's best path is to re-issue tokens
  (process reissue flow, future pack). Old tokens keep showing the old
  name until natural expiry.
- Rules out: per-request `Application.findById(name)` lookup (latency,
  write amplification after rename).

4. "Should the old `callerId` field be renamed in one shot or kept as alias
for one version?"

Answer:
- One shot, no alias. Rename `callerId` to `applicationId` everywhere in
  the same release. Drop `CallerIdentity.callerId`; introduce
  `CallerIdentity.applicationId` and `CallerIdentity.applicationName`.
  Rename `TokenClaims.sub.callerId` to `sub.applicationId` and add
  `sub.applicationName`.

Why:
- Pre-1.0. No production users. The codebase is small enough to update
  in lockstep.
- Aliases accumulate debt. The "Nothing Is Special" principle
  (PHILOSOPHY.md) argues against keeping aliases for what is just a
  name — they become load-bearing over time.
- Tests update in the same change. The risk is mechanical, not
  architectural.
- Rules out: `callerId` retained as a deprecated alias for one version
  (dead code grows).

5. "Wire protocol: SDK sends `appName` in auth, or just relies on token?"

Answer:
- Just the token. `sdk.auth` message stays the same shape as today:
  `{type: "sdk.auth", token}`. No `appName` field on the request.
- The server validates the token, extracts `applicationId`, registers
  the connection under that id. The server does NOT consult the
  Application store to "resolve" anything — the token claim IS the
  source.
- The server's response `sdk.auth.ack` returns
  `{ applicationId, applicationName }` so the SDK can log and persist
  the id locally for future reconnects.

Why:
- The SDK got the token from `auth.token.issue`, which already bound
  an applicationId. The token IS the identity. No resolution needed.
- Self-describing wire would be redundant: the SDK already knows who
  it is (it just got the token).
- Multi-app SDK processes (one process hosting multiple apps) open
  one connection per app, each with its own token. The registry keys
  by applicationId, so each connection is uniquely scoped.
- Rules out: `appName` field on the auth request (server-side resolution
  step that the token already covers).

6. "Capability owner shape: `backend-sdk-${tenantId}:${applicationId}` or
`${tenantId}:${applicationId}` (no prefix)?"

Answer:
- `backend-sdk-${tenantId}:${applicationId}` (string with the prefix).
- The `backend-sdk-` prefix remains the dispatch discriminator (the
  gateway routes `backend-sdk-*` owners to backend-runtime; `plugin-*`
  owners to plugin-manager; `gateway-*` to platform caps). Removing the
  prefix requires restructuring `CapabilityRecord.owner` to a structured
  type — that's a separate refactor.
- The colon between `tenantId` and `applicationId` is a parseable
  separator. The dispatch path parses:
  ```
  /^backend-sdk-([^:]+):(.+)$/.exec(owner)
  ```
  and extracts `(tenantId, applicationId)`. The connection registry key
  is `${tenantId}:${applicationId}` (the same composite, minus the
  prefix).

Why:
- Minimal change to the existing dispatch routing logic. The discriminator
  stays at the front of the string.
- Stable across all owner types (`backend-sdk-*`, `plugin-*`, `gateway-*`,
  `runtime-*`). Each prefix maps to a dispatch backend.
- The structured-owner migration (`{kind, tenantId, applicationId}`) is
  a future cleanup; deferred until the whole set of ownership shapes is
  surveyed.
- Rules out: structured owner field (too big a refactor for this pack),
  naked `${tenantId}:${applicationId}` (breaks prefix-based dispatch).

7. "Rate-limit bucket key: include `applicationId` or keep tenant+callerId
dual-key?"

Answer:
- Bucket key: `${tenantId}:${applicationId}`. Drop the legacy `${tenantId}:${callerId}` shape.
- Two SDKs from the same app share the bucket (same identity). Two apps
  in the same tenant get separate buckets. This is the natural
  per-application unit.

Why:
- Fits the new identity model. The applicationId is the scope of the
  rate limit.
- Per-user (per-callerId) limits are a future feature if needed; not
  in v1.
- The current dual-key was an alias for the old shape (callerId == appId).
  Drop it cleanly.
- Sources: gateway-core/src/rate-limit.ts:19 (per-(tenantId, callerId)
  comment), audit Section 2.1 (unbounded buckets — sweep already
  landed in D-38).

8. "Should Application lifecycle events be emitted on the event bus?"

Answer:
- Yes. Emit `application.created`, `application.renamed`, `application.removed`
  on the event bus, mirroring the `tenant.*` event shape (the existing
  convention in `CONTEXT.md` for lifecycle events).
- SDKs do not need to subscribe by default (the platform removes the
  application server-side). The events are for dashboards, audit
  consumers, and the CLI.

Why:
- A first-class entity should have first-class lifecycle events. Matches
  the convention used by tenant.* and session.* in CONTEXT.md.
- Dashboards can show creation/rename history without polling.
- Rules out: no events (asymmetric with tenant.* and session.*;
  consumers would have to poll).

9. "What happens when an Application is removed?"

Answer:
- The server forcibly closes every SDK connection registered under that
  applicationId. Each socket gets a `close` with code 1000 and reason
  `application-removed`.
- Every in-flight invocation owned by that application is rejected with
  `GATEWAY_APPLICATION_REMOVED` (retryable: false — the SDK cannot retry
  a token whose app is gone).
- The SDK's responsibility: re-`auth.token.issue` (which auto-creates a
  new Application if the operator deleted one with the same name; errors
  if the name was unambiguous to the deleted app).

Why:
- Operator action is explicit (delete = gone). The SDK has a clear
  signal to re-authenticate.
- `GATEWAY_APPLICATION_REMOVED` is distinct from generic
  `GATEWAY_INTERNAL_ERROR` so the SDK can branch on cause.
- The retryable=false flag prevents a retry storm from the SDK after
  deletion.
- Rules out: leave connections open and serve traffic (silent stale
  references), reconnect on next heartbeat (delayed visibility).
