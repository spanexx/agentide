## What doesn't work (verified FAIL)

### 1. `agentide invoke` requires a session that nothing creates

**Severity:** Critical. Blocks every CLI-driven business invocation.

**Reproduce:**
```bash
agentide invoke product.list --args '{}' --url ws://127.0.0.1:7300/ws --token "$TOKEN"
# error: GATEWAY_SESSION_REQUIRED — capability "product.list" requires a session
```

Same error for `product.create`, `user.register`, `cart.view`, `order.list`, etc. No way to pass a session because the CLI doesn't auto-create one and doesn't expose a single command to mint a session id.

**Evidence in code:** `packages/agentide/src/consumer.ts:runInvoke` accepts `--session` but never mints one when omitted.

**Fix recommendation:** when `--session` is omitted, the CLI should `session.create` → capture the id → wrap the invoke in that session → return the result. One round-trip, transparent to the operator. Simpler: a top-level `agentide session create` alias and print the new id for operators who want to talk to multiple caps in one session.

### 2. CLI `--url` guidance is port-ambiguous; 7350 is the **wrong door**

**Severity:** High. Every new operator hits this on their first remote command.

**Reproduce 1 (CLI help):**
```bash
agentide --help
# ...
# common flags: --url <ws://host/ws> --token <jwt|path:/...> --json
```

**Reproduce 2 (silent hang):**
```bash
agentide sessions --url ws://127.0.0.1:7350/ws --token "$TOKEN"
# (15s timeout, then exit — no message at all)
```

**Reproduce 3 (works on the right port):**
```bash
agentide sessions --url ws://127.0.0.1:7300/ws --token "$TOKEN"
# []
```

**Why:** `agentide start --port-sdk 7350` binds TWO websocket doors:
- `:7300` — `adapter-websocket` (the **consumer protocol** the CLI uses; auth handshake + invoke frames).
- `:7350` — backend-runtime / SDK door (`sdk-node`, `sdk-browser`, first-frame `{type:"sdk.auth"}` protocol).

The CLI's consumer code (`packages/agentide/src/consumer.ts:runConsumer` → `createWsClient({ url, token })` → `adapter-websocket/dist/client.js`) speaks the consumer protocol on `:7300`. The SDK door accepts only the SDK auth handshake, so the CLI handshake stalls and the operator gets a silent 15-sec timeout (or longer).

**Fix recommendation:**
- Update the help line to `--url <ws://gateway-host:7300/ws>` (or whatever the resolved port is).
- Better: detect the door from the gateway and emit a clear error when the server doesn't speak the consumer protocol within a few seconds (e.g. `error: --url points to the SDK door (port 7350); the CLI consumer needs the websocket adapter (port 7300).`).
- The example app's `.env` uses `PLATFORM_GATEWAY_URL=ws://127.0.0.1:7350` correctly — that's the SDK door. The two are different protocols.

### 3. `agentide init` doesn't create the data dir

**Severity:** High (first-run UX).

**Reproduce:**
```bash
rm -rf /tmp/foo
agentide init --data-dir /tmp/foo --default-tenant acme
# error: ENOENT: no such file or directory, open '/tmp/foo/gateway-secret'
# exit 1
```

**Why:** `packages/agentide/src/cli.ts:runInit` calls `createPlatform({ dataDir, ... })` directly. The platform's `loadOrCreateSecret` opens a file inside the dir without first ensuring the dir exists. Compare with `packages/agentide/src/start.ts:118-132` (CID:start-003) — the same code path on `start` has a friendly probe that prints:
```
error: data dir /tmp/foo not writable or missing: ENOENT ...
(create the directory first: mkdir -p /tmp/foo)
```

**Fix recommendation:** at the top of `runInit`, do `await fs.mkdir(dataDir, { recursive: true })` (via the platform's FileSystem adapter or directly via `node:fs/promises` since the CLI is Node-only). Or at minimum, emit the same `mkdir -p` hint that `start` does.

### 4. `agentide status` (no `--data-dir`) assumes a cwd-local default

**Severity:** Medium.

**Reproduce:**
```bash
# Gateway started with --data-dir=/tmp/ag-e2e/data
# status from a different cwd:
cd /tmp
agentide status
# error: ENOENT: no such file or directory, open './.agentide/data/gateway-secret'
# exit 1 (was the operator expecting a status report!)
```

**Why:** `cli.ts:runStatus` calls `createPlatform({ dataDir })` with the default data-dir resolver. The default is `process.cwd() + '/.agentide/data'`. The `start` command's pid file at `/tmp/agentide.pid` doesn't track the data-dir the child was started with.

**Fix recommendation:** either (a) write the `data-dir` into the pid file at start time and read it back in `status`, or (b) default `status` to the last-used data-dir (e.g. `~/.agentide/last-data-dir`), or (c) make the help page explicit: `status` requires `--data-dir` to match the gateway's.

### 5. Dashboard `app.js` is the P3 placeholder (81 bytes)

**Severity:** Medium (already known; verified still broken in 0.3.1).

**Reproduce:**
```bash
curl -s http://127.0.0.1:7200/assets/app.js | head -c 100
# // P3 placeholder — P4 will replace with the full vanilla-JS dashboard client.
```

**Why:** `packages/dashboard-core/src/server.ts:resolveAssetsDir()` builds a candidate list from the server's `__dirname` (e.g. `here/assets`, `here/../src/assets`, `here/../assets`, `cwd`). After `npm install -g @spanexx/dashboard-core`, the published layout is `node_modules/@spanexx/dashboard-core/src/assets/` — none of the candidates match. The HTML loads, but the SPA client is the 81-byte placeholder.

**Fix recommendation:** add `node_modules/@spanexx/dashboard-core/src/assets/` (or determine the real path via `require.resolve("@spanexx/dashboard-core/package.json")` and walk up to its root) to the candidates list. Then cut a `dashboard-core` patch release.

### 6. `client grant` flags don't match the help

**Severity:** Low.

**Reproduce:**
```bash
agentide client grant --client-id cli_xxx --scope 'acme:*' --data-dir /tmp/ag-e2e/data
# client grant requires --tenant and --name
```

**Why:** The CLI expects `--tenant` and `--name` (the client's *display name*?), not `--client-id`. The help line (`agentide client --help`) shows six subcommands in a row without per-subcommand detail, so I had to guess. The grant subcommand legitimately needs different flags than the rest of the client subcommands.

**Fix recommendation:** per-subcommand help (already standard CLI UX). E.g. `agentide client grant --help` should show only the flags grant needs.

---

### 7. `agentide stop` exit codes inconsistent for "nothing running"

**Severity:** Low.

**Reproduce:**
```bash
# State: pid file present, pid is dead.
agentide stop
# Gateway (PID 1170760) was already not running. Pid file removed.
# exit 0

# State: pid file gone.
agentide stop
# no gateway running (no pid file at /tmp/agentide.pid)
# exit 1
```

Both states convey "there's nothing to stop." Pick one exit code (0 is friendlier for `&&` chains). The current `0` for "already not running, cleaned up pid file" is at least defensible — `stop` *did* a side effect (cleanup). The `1` for "no pid file" reads like a real error.

**Fix recommendation:** unify on 0 (success / nothing to do) for both branches; or document the distinction.

## Cross-cutting observations

**`--data-dir` is now correctly honored.** The 2026-08-05 handoff recorded that `--data-dir=/tmp/foo` was silently dropped (default `./.agentide/data` was used). In 0.3.1, with the `--flag=value` parser fix (PR #54), the flag works as expected. The test confirmed: start banner named the right path, no fallback `./.agentide/data` was created, and --data-dir was the only candidate for state.

**Detached-start fix holds.** PR #54's `CID:start-013` (env-var bypass for the gateway child) works as designed. The gateway child boots, listens on all three doors, and `status` reports it.

**Dashboard HTML is correct, only the JS client is placeholder.** 1052 bytes returned, `<title>Agentide Dashboard</title>` confirmed. The issue is purely the asset resolution path.

**Watch on `*.list` did not capture events.** `agentide watch capabilities --topic '*.list'` ran for 5s while `product.list` was invoked; the buffer was empty. Either (a) the topic pattern doesn't match the emitted topic, (b) the watch semantics require a session like `invoke` does, or (c) the event is emitted but the alias doesn't subscribe. Worth a follow-up — not blocking.

**Example app's `.env` PLATFORM_TOKEN is 1 hour expiry.** The token in `example/.env` has `iat: 1785992678188` / `exp: 1785996278188` (exp = iat + 1h). If you don't refresh it, the SDK reconnect (after a gateway restart) fails auth. The example is a demo, so this is intentional, but it's a footgun for first-time users.

## How to reproduce

```bash
# Run UNSANDBOXED — gateway binds loopback ports and the sandbox blocks raw sockets.
DD=/tmp/ag-e2e/data
mkdir -p "$DD"
agentide init --data-dir "$DD" --default-tenant acme
TOKEN=$(agentide token issue --tenant acme --caller cli --data-dir "$DD" | grep -oE 'eyJ[A-Za-z0-9_.-]+' | head -1)
agentide start --data-dir "$DD" --no-mcp --port-sdk 7350 --dashboard-port 7200
sleep 5
# IMPORTANT: use the WEBOCKET ADAPTER port, not the SDK door.
agentide sessions --url ws://127.0.0.1:7300/ws --token "$TOKEN"   # []  exit 0
agentide health --url ws://127.0.0.1:7300/ws --token "$TOKEN"     # {"status":"ok"}  exit 0
# invoke needs a session (this is the Critical issue)
agentide invoke product.list --args '{}' --url ws://127.0.0.1:7300/ws --token "$TOKEN"
# error: GATEWAY_SESSION_REQUIRED ...
agentide stop
```
