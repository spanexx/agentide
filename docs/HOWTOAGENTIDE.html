How to Agentide

Install the agentide binary from npm, boot a gateway, register capabilities from your backend SDK, and let agents (Claude Code, MCP-CLI, custom apps) call them. One CLI does everything.

1. What is Agentide

Agentide is an operating system for AI agents. Instead of exposing raw REST endpoints or wiring applications to a single agent protocol, you expose capabilities — named, typed, permission-scoped actions that any compatible AI agent can discover and invoke through any of the platform's adapters.

The architecture splits into two planes:

  • Control Plane — the Gateway, Session Manager, Capability Registry, and Plugin Manager. Decides what should happen and whether it's allowed. It does not execute capabilities.
  • Execution Plane — the runtimes (Backend Runtime, Browser Runtime, future Docker/Git/File/Kubernetes/Database runtimes). Executes the work, owns the resources.

Adapters are pure protocol translators at the edge — MCP, WebSocket, CLI, REST — they contain no business logic. MCP is one adapter, not the foundation. The Capability Registry is the central surface; applications register capabilities (the way you expose functionality to agents), and runtimes execute them. Sessions are execution contexts that own runtime resources — not chat history — and clean up automatically on destroy.

Instead of: 

GET /customers
POST /orders
DELETE /products

applications expose:

customer.read
customer.create
order.submit
inventory.update

The gateway decides how those capabilities are executed. Agents interact with capabilities, never directly with APIs.

One-liner (recommended)

Requires Node 20+.

npm install -g @spanexx/agentide

You should now have agentide on your PATH. Verify:

agentide --version       # should be 0.1.1
agentide --help

Alternative: install.sh

Detects your OS and installs the right binary (or Docker image, or npx fallback). Hosted on GitHub raw:

curl -fsSL https://raw.githubusercontent.com/spanexx/agentide/main/packages/agentide/install.sh | bash

(requires the spanexx/agentide repo to be public — if you fork or self-host, change the URL.)

Backend SDKs

For a node/TypeScript backend (covers most node apps), install the SDK:

npm install @spanexx/sdk-node

For a browser app (react/vue/svelte):

npm install @spanexx/sdk-browser

CJS variants (@spanexx/sdk-node-cjs, @spanexx/sdk-browser-cjs, @spanexx/event-bus-cjs, @spanexx/agentide-cjs) currently publish at 0.0.x — their build pipeline is broken (mirrored source has undeclared deps). Use the ESM packages on the right-hand side. The CJS variants will refresh in a follow-up pack.

3. Start the gateway

The gateway listens on two ports:

portprotocolused by
7100MCP (HTTP + JSON-RPC)Claude Desktop, MCP-CLI, AI agents
7300WebSocket at /wsSDKs (sdk-node, sdk-browser), the CLI

agentide start detaches by default (background daemon). It returns immediately and writes the child PID to --pid-file (default /tmp/agentide.pid) and logs to --log-file (default /tmp/agentide.log). Both files live under /tmp so reboots wipe them automatically — no stale state.

First run

Pick a data dir (defaults to ~/.agentide/data) and start:

agentide init   --data-dir ~/.agentide/data --default-tenant acme
agentide start  --data-dir ~/.agentide/data --default-tenant acme

You'll see:

Detached. PID: 48211. Logs: /tmp/agentide.log. Stop with: agentide stop.

Watch the log:

tail -f /tmp/agentide.log

Stop it:

agentide stop

Need foreground debugging? Use --foreground:

agentide start --foreground --data-dir ~/.agentide/data

Available flags

flagdefaultwhat it does
--data-dir <path>~/.agentide/datawhere the secret + tenants + audit log live
--bind <ip>127.0.0.10.0.0.0 for network access
--port-mcp <n>7100MCP listener port
--no-mcp / --no-wsoffdisable the respective adapter
--default-tenant <id>nonebootstrap a tenant on first start (idempotent)
--pid-file <path>/tmp/agentide.pidwhere start writes the child PID
--log-file <path>/tmp/agentide.logwhere the daemon writes its output
--foregroundoffrun in the current terminal (blocks)
--enable-oidcoffexpose the OIDC dev-stub on the MCP adapter (see §8)
--no-tlsoffdisable TLS enforcement on the OAuth token endpoint (localhost dev only)
What gets written to the data dir?
  • gateway-secret — HS256 signing key for tokens. generated on first run.
  • tenants.json — list of tenants the gateway knows about.
  • audit.log — append-only log of every capability invocation.
  • clients/ — per-client directory holding .secret-<id>.txt (mode 0600) at create time (see §8).

4. Mint a token

The gateway mints JWTs. Tokens are how callers prove they're allowed to invoke caps. Two flavors:

kindhowused by
admin tokenagentide token issue ... (full scope)you, the operator, anyone with the secret
consumer tokensame command, narrow scopeyour backend SDK, agent harnesses

agentide init prints the bootstrap token to stdout inside an ANSI reverse-video block. It auto-clears (overwrites scrollback with a blank screen) when you press Enter, or after 30 seconds (constant TOKEN_CLEAR_MS = 30_000 in packages/agentide/src/lifecycle.ts), whichever comes first. The token is not written to any file. In a non-TTY (CI, pipe, redirect) the print-and-clear step is skipped.

Example: minimal admin token for the SDK

agentide token issue \
  --tenant acme \
  --caller nest-app \
  --scope '*'

Output is a single JWT line. Copy it.

Example: narrow token for a browser-bound SDK

Browser clients must carry an expectedOrigins claim; the server enforces exact-match on the upgrade Origin header (deny-by-default for browsers, Node bypass). Repeat --origin for multiple URLs, or use --origins for a comma list:

agentide token issue \
  --tenant acme \
  --caller product-reader-agent \
  --scope 'product.read' \
  --origin http://localhost:7200 \
  --origin http://127.0.0.1:7200

This token can only call product.* caps with a read tier, and only from those origins.

5. Wire your backend SDK

The SDK is @spanexx/sdk-node. It's a single function: createSdk(config) with a manifest + handlers map. The SDK connects to the gateway over WebSocket, registers the capabilities, and dispatches inbound invocations to your handlers. No NestJS adapter, no forRoot, no module — just a function.

envpackageuse case
server (ESM)@spanexx/sdk-nodets-node, deno, modern module-only
browser (ESM)@spanexx/sdk-browseresbuild/vite/rollup ESM

Avoid the -cjs siblings for now — they publish at 0.0.x while the build bug is fixed.

Example: a Node backend that exposes product + user caps

TypeScript (the SDK is shipped as ESM with full types):

import { createSdk } from "@spanexx/sdk-node";

// Two minimal caps: a read and a write.
const manifest = {
  app: "node-ecommerce",
  capabilities: [
    { name: "product.list",  version: "1.0.0", tier: "read",  permissions: ["*"] },
    { name: "product.create", version: "1.0.0", tier: "write", permissions: ["*"] },
    { name: "user.register",  version: "1.0.0", tier: "write", permissions: ["*"] },
  ],
};

const handlers = {
  "product.list": async () => {
    const items = await db.product.find({ active: true });
    return { items, count: items.length };
  },
  "product.create": async (input: { sku: string; name: string }) => {
    return db.product.insert(input);
  },
  "user.register": async (input: { email: string; password: string }) => {
    return db.user.insert({ ...input, passwordHash: await hash(input.password) });
  },
};

const sdk = createSdk({
  gateway: { url: "ws://127.0.0.1:7300/ws", token: process.env.PLATFORM_TOKEN! },
  app:     { id: "node-ecommerce", name: "node-ecommerce" },
  manifest,
  handlers,
  observability: { logger: createSdk.logger() },
});

await sdk.connect();

Inside Express, Fastify, NestJS, or any other framework: call await sdk.connect() on boot — the SDK opens a WebSocket, registers the manifest, and stays connected. Each invocation arrives as a function call to the matching handler.

The two mandatory fields of every manifest:

  • app — a non-empty string identifying your app.
  • capabilities — an array. Each entry must declare name, version, tier (read / act / destructive for runtime caps; read / write for platform caps; omit for business caps), and permissions (use ["*"] for dev, granular strings for prod).

6. Wire your browser SDK

The browser SDK is annotation-driven: tag DOM elements with data-sdk-cap="<capability.name>", the SDK observes them via MutationObserver, registers them with the gateway, and the page's UI becomes a thin client to the backend caps.

import { createSdk } from "@spanexx/sdk-browser";

const sdk = createSdk({
  gateway: { url: "wss://gateway.example.com/ws", token: "<jwt-from-server>" },
  app:     { id: "web-storefront", name: "web-storefront" },
  defaultTier: "act",
  defaultVersion: "1.0.0",
});
await sdk.connect();
// anywhere in your HTML:
// <button data-sdk-cap="cart.add" data-sdk-args='{"sku":"ABC123"}'>add to cart</button>

The server-rendered page mints a per-user token (with HTTP-only cookie binding the session), ships the token in the HTML, and the SDK connects on page load. For browser clients, the token must carry an expectedOrigins claim — the server enforces exact-match on the upgrade Origin header (deny-by-default for browsers, pass-through for Node). Mint this server-side with agentide token issue --origin <url>.

7. Call a capability

Three ways to invoke a registered capability.

a) from an MCP-compatible agent (Claude Desktop, MCP-CLI)

Configure your agent to point at http://127.0.0.1:7100/mcp, with a JWT in the MCP config. The agent sees your caps as tools.

b) from the CLI

agentide invoke product.list '{}'
agentide invoke product.create '{"sku":"ABC123","name":"widget"}' \
  --session my-session-id

Use --json for machine-readable output, omit for human tables.

c) from another backend via the SDK

const sdk = createSdk({ gateway: { url: "ws://127.0.0.1:7300/ws", token: "..." }, ... });
const result = await sdk.invoke("product.list", { userId: "u_42" });

8. Client credentials (machine identity)

Unattended backends (Node apps, workers, CI jobs) shouldn't paste a human-minted JWT into .env. Instead, register a client — a machine identity — and let the SDK mint + refresh its own tokens via the OAuth client_credentials grant. The gateway stores only a salted hash of the secret; the plaintext is shown exactly once at creation.

a) create a client (operator)

agentide client create --tenant acme --name node-app --scope 'product.*'

Prints the client id and the path to the secret file (<data-dir>/clients/.secret-<id>.txt, mode 0600). Copy the secret into the app's .env — the gateway cannot show it again. Rate limit: 5 creates per operator per hour (constant CREATE_RATE_LIMIT_MAX = 5 in packages/gateway-core/src/client-service.ts:42).

b) SDK mints + refreshes its own tokens

import { createSdk } from "@spanexx/sdk-node";

const sdk = createSdk({
  gateway: { url: "ws://127.0.0.1:7300/ws" },   // no token here — SDK will mint one
  app:     { id: "node-app", name: "node-app" },
  manifest: "manifest.json",                       // or inline: { app, capabilities: [...] }
  handlers: handlers,
  oauthUrl:    "http://127.0.0.1:7100",           // base for POST /oauth/token
  clientId:    "cli_xxx",
  clientSecret: process.env.PLATFORM_CLIENT_SECRET,
  onRevoked: () => { console.error("client revoked, exiting"); process.exit(1); },
});
await sdk.connect();   // POSTs client_credentials, stores the JWT, connects

Environment variables PLATFORM_CLIENT_ID and PLATFORM_CLIENT_SECRET work too. The SDK refreshes the token before expiry (60s window + jitter, one in-flight refresh at a time). If the operator revokes the client, the next refresh gets client_revoked, the SDK closes the WebSocket cleanly and stops reconnecting (your onRevoked callback fires).

c) offline handoff: registration codes

No secret to paste? Grant a one-time code, redeem it on first boot:

agentide client grant --tenant acme --name node-app --scope 'product.*'
# → code: rc_xxx  (valid 5 min, one-time use)
agentide client redeem --code rc_xxx
# → client_id + client_secret — save these into config.toml

d) revoke / rotate

agentide client revoke --client-id cli_xxx   # instant: next token mint → 401 client_revoked
agentide client rotate --client-id cli_xxx   # new secret; old one valid 5 min grace

e) humans: OIDC auth-code grant (dev stub)

Start the gateway with --enable-oidc to expose GET /oauth/authorize + GET /oauth/callback on the MCP adapter — a dev-stub approval page issues a JWT via the auth-code flow (one-shot codes). Off by default; swap the stub for a real IdP (Auth0, Keycloak) in production. --no-tls disables TLS enforcement on the token endpoint (localhost dev only).

9. All commands

Operator (run on the host where the gateway lives)

commandwhat it does

agentide startlaunch the gateway as a detached daemon (returns PID + log path)

agentide statusin-process when no remote config; gateway.status when --url given

agentide token issue --tenant ...mint a JWT (supports --origin / --origins for browser tokens)
agentide capability listlist registered cap names (in-process)
agentide capability describe --name <n>show one cap's record (in-process)
agentide plugin listinstalled plugins (runtime, service, observer)
agentide client create --tenant <id> --name <n> [--scope '<s>']register a machine identity (see §8)
agentide client grant/redeemone-time registration-code handoff (offline-friendly)
agentide client list/revoke/rotatemanage machine identities (rotate keeps 5-min grace)

Consumer (call against a running gateway)

These commands run against a remote gateway. They require --url, PLATFORM_GATEWAY_URL, or a config file to point at the WebSocket. They're aliases for the underlying capability calls.

commandwhat it does
agentide capabilitieslist caps on the gateway (alias for capability.list)
agentide sessionslist active sessions
agentide pluginslist runtime-installed plugin caps
agentide statusgateway uptime, plugin count, etc. (remote gateway.status)
agentide health{"status":"ok"} ping
agentide invoke <cap> [--args '<json>'] [--session <id>] [--mode call|stream]universal pull
agentide watch <alias> [--topic <pattern>]live event stream (NDJSON, Ctrl-C to exit)

Common flags

--url <ws://host/ws>        # default ws://127.0.0.1:7300/ws (config file wins)
--token <jwt | path:/...>   # override the token (env PLATFORM_TOKEN works too)
--config <path-to-toml>     # config file override (defaults to <os-config-dir>/platform/config.toml)
--json                       # machine-readable output (one line)

10. Troubleshooting

error: port 7100 already in use (is another gateway running?)

Either kill the other process or move the new one:

agentide start --port-mcp 17100

(The WebSocket port is fixed at 7300 in v1; see packages/agentide/src/start.ts:54 for the rejection.)

error: --port-ws is not supported yet

v1 hardcodes the WS port at 7300. The platform factory has no adapterWsPort field — only wsPort on CreatePlatformConfig (consumed at factory-time, not from the CLI). The start command rejects --port-ws at parse time. To change the port today, set wsPort programmatically in createPlatform({ ... }) or wait for the future schema field.

error: token required (--token, PLATFORM_TOKEN, or config file)

Consumer commands need auth. Either pass --token, set PLATFORM_TOKEN, or create <os-config-dir>/platform/config.toml:

gateway_url = "ws://127.0.0.1:7300/ws"
token       = "<jwt>"
error: token invalid

The JWT signature doesn't match the gateway's secret. Two main causes:

  1. the secret changed (wiped ~/.agentide/data/gateway-secret) since the token was minted — re-mint.
  2. wrong gateway — the token was minted for a different tenant/scope. Check --tenant and --scope on the token issue.
error: auth.error "origin mismatch" (websocket adapter)

The browser client sent an Origin header that doesn't match the token's expectedOrigins claim. Either mint the token with the correct origin (server-side, before the page loads) or relax the mismatch in dev. The server enforces exact-match on the upgrade Origin header — no prefix or wildcard.

capability.list returns empty []

Two meanings: (a) no backend SDK has booted against this gateway yet. (b) all registered caps are filtered out by your token's scope or the --owner filter. Check that your token's --scope includes the cap you're looking for.

GATEWAY_SESSION_REQUIRED on invoke

The cap requires a session and none was attached. Pass --session <id> or the consumer's sessions handle. Some plugins auto-spawn a session; business caps can be invoked without one when scoped appropriately.

Quick mental model (recap)

On your laptop / server

You install agentide once. You start it once. It binds two ports and writes a few files under ~/.agentide/data (the gateway secret, tenants, audit log, plus clients/ for machine identities). It doesn't do anything interesting by itself.

In your backend

Your app imports the SDK, declares its caps in a manifest, and connects. The gateway registers them. Agents discover them. They get called.
