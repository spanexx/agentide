## Contract Gaps

### Gap 1: `createAdapterPipeline` setup shape differs from the locked A1 signature

**Expected (from PRD-TRD):**
> `createAdapterPipeline({gateway, config, input, output, errors, response})` (A1) — the shared invocation pipeline. Emits **no events**; imports `@spanexx/gateway-core` at runtime.

> A1 (Q3): one call — `createAdapterPipeline({ gateway, config, input: parse(), output: render(), errors: table, response: strategy })` — returns the door's ready-to-use handlers.

**Found (in code):**
```typescript
export interface AdapterPipelineOptions {
  readonly gateway: Gateway;
  readonly errors: ErrorConverter;
  readonly response: (correlationId: string) => ResponseChannelSink;
}
// pipeline.ts comment: "config passthrough is omitted in v1 — per-invocation
// input/output flow through invoke() args, errors via the shared ErrorConverter"
```

**Plain English:** The plan promised a six-key setup where the door hands in its own `parse`/`render` functions and a config object; the shipped pipeline takes three keys (`gateway`, `errors`, `response`) and receives input/output per-invocation via `invoke({correlationId, token, name, input, sessionId, mode})`. Behaviorally the pipeline still does parse → gateway → render → terminal frame, so doors get what they need, but the call shape a door author copies from the docs doesn't exist. Anyone following PRD-TRD will write code that fails to compile.

**Recommendation:** update PRD-TRD (Technical Design → API Contracts) to the shipped three-key shape and record the deliberate "config/input/output as invoke args" scoping decision as an A1 amendment; optionally log drift.

### Gap 2: "lazy" auth mode is a knob without lazy behavior

**Expected (from PRD-TRD / A2):**
> Auth policy (A2): `{mode: "early" | "lazy"}` knob; early verifies once at open and caches identity; auth-failure behavior frozen (wire phrases stay door-local).

> A2 (Q1): one knob — `auth: { mode: "early" | "lazy" }`. `lazy` = token rides through, kernel verifies per call. A2 (Q2): a pipeline `re-verify(token)` call for mid-connection refresh.

**Found (in code):**
```typescript
const mode: AuthPolicyMode = options.mode ?? "early";
// auth-policy.ts comment: "lazy is the knob for doors that defer verification
// to first invoke; v1 behavior is identical for both (deferred verification
// ships with a consumer that needs it)."
```
`createAuthPolicy({mode:"lazy"})` calls `verifyToken` immediately, exactly like `"early"`. The `AuthPolicy` interface has no `re-verify(token)` method — a second `authenticate()` call serves the refresh case.

**Plain English:** The knob exists and is part of the canonical surface, but both modes do the same thing today. No current door uses lazy (WS uses early), so nothing observable changes — but the A2 contract promised "token rides through, kernel verifies per call" semantics, and the deferred behavior is deferred to find a consumer. That is a documented-in-code shortening of the design, not a wire-visible difference.

**Recommendation:** log drift (accepted for v1, deferred until a lazy consumer exists — suggestion A8/MCP or REST); optionally update PRD-TRD to say "lazy is exported but deferred in v1".

but direct runs: `Test Files 7 passed (7) / Tests 50 passed (50)` (core) and `Test Files 10 passed (10) / Tests 54 passed (54)` (WS).

Both sims exist; the design sim was archived because it no longer compiles against the shipped surface — wait, it is a doc script. Reality:
- Move map (pre-impl Step 2): identical to what shipped — `readClaims`, auth policy, response channel, error converter, RecordRegistry, capability lookup moved; `protocol.ts`/`errors.ts`/`queue.ts`/`fanout.ts`/`registry.ts`/`client.ts`/`types.ts` stayed with the exact surface. ✓

Accepted — zero-delta contract outranks pure A1 re-export purity. Log as a known future narrowing (MCP migration A8).
